# Phase 8 security audit

Audit date: 14 November 2026, Asia/Kolkata. Scope: repository, installed framework guides, local configuration metadata, isolated PostgreSQL/API/browser tests and local production build. This is a source and regression audit, not an independent penetration test or certification of a hosted environment. See [execution results](phase-8-test-results.md) and [release gates](phase-8-release-readiness-checklist.md).

## Findings requiring release action

Severity describes the risk of an Internet launch with the control absent. An unverified hosting control is not a claim that an exploit was demonstrated locally.

| ID     | Severity                                       | Evidence and implication                                                                                                                                                                                                                                                                                                                      | Required action / owner                                                                                                                                                                                                                                                                                  |
| ------ | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-01 | High                                           | `src/server/auth/config.ts` provides password authentication/recovery but no email ownership verification workflow or privileged-user MFA. The auth route allowlist has no verification/MFA endpoints. `docs/operations.md` requires a verified identity for production owner promotion; merely flipping `emailVerified` is not verification. | Owner/security lead must approve and implement or independently establish the required identity and privileged-access controls before Internet launch. Adding these workflows is outside this audit's no-new-features scope. Do not bypass the promotion guard.                                          |
| SEC-02 | High if local bootstrap credentials are reused | Local setup deliberately creates a PostgreSQL bootstrap superuser. Database URL validation accepts PostgreSQL URLs; the application does not prove least privilege or enforce verified remote TLS. Local connectivity therefore supplies no production database-security assurance.                                                           | Hosting operator must provision separate runtime, migration and operator roles, restrict network access, prove runtime cannot alter schema/roles/triggers, and verify the selected driver's certificate-validating TLS configuration for remote connections. Never copy local credentials to production. |
| SEC-03 | High release gate, hosted state unverified     | No production ingress, secret store, SMTP delivery verification, protected offsite backup, monitoring or restore environment is configured by this audit. `APP_ENV` defaults to development; a production Next build alone does not activate application production guards.                                                                   | Operator must explicitly inject `APP_ENV=production`, HTTPS canonical auth URL, unique secrets and SMTP sender/provider settings. Verify ingress, secure cookies, backup access/encryption/restore and alert routing in the chosen environment.                                                          |
| SEC-04 | Medium                                         | The application CSP blocks framing, objects and foreign base URLs, but has no general `script-src` restriction. No HSTS header is supplied by `next.config.ts`.                                                                                                                                                                               | Review a tested production CSP and HTTPS/HSTS policy with the selected ingress. Do not insert an untested CSP that breaks existing Next scripts, images or forms. HSTS must reflect the actual HTTPS/subdomain policy.                                                                                   |
| SEC-05 | Medium                                         | Authentication and enquiry throttles exist; uploads/reporting rely on authentication, finite body/image/query bounds and connection/transaction limits. No production ingress concurrency/body/timeout controls or load evidence exist.                                                                                                       | Operator must configure request size/time/concurrency limits and exercise representative report/image traffic in staging. Ensure the trusted client-IP header is overwritten by ingress; otherwise preserve the conservative shared limiter.                                                             |

SEC-01 remains an application security prerequisite. SEC-02/03 are critical deployment gates, not failures of the isolated local environment. No permission was granted to create identity features, infrastructure, external accounts or send real recovery email during this audit.

Inspected configuration metadata confirms `.env` uses `APP_ENV=development`, file mail and an HTTP application URL; `.env.test` uses test mode, file mail and HTTP. Both database hosts are loopback, with no SSL mode specified in their URLs. These are local configurations, not production templates. Only this non-secret metadata was recorded in `.local/phase8-audit/config-metadata.json`; credentials were not printed.

## Controls reviewed

| Area                          | Implementation and audit evidence                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Roles / administration        | `src/server/permissions/service.ts` re-reads current role and active status from PostgreSQL; cookie role input is not authoritative. API routes and business services enforce explicit permissions. Only Super Admin receives financial valuation/profitability, catalogue writes, settings changes, receipt reversals and dispatch corrections. Public registration rejects role input.                 |
| Data isolation                | Customer addresses, carts, orders, payments and delivery views use the current customer ID. Foreign order/address/proof requests are rejected. Global reports, expense receipts and admin actions deny customer/dealer/sales-rep access. Approval status controls current dealer pricing/access; historical order categories remain frozen.                                                              |
| Sessions / recovery           | Passwords use Better Auth hashing; 12–128 character bounds; database sessions and rate limiting; no cookie session cache; seven-day session lifetime. Suspension and reset revoke sessions. Recovery tokens are hashed, expire in 30 minutes and are single-use. Secure/HttpOnly/SameSite=Lax cookies are exercised with a synthetic HTTPS origin; this does not prove real ingress TLS.                 |
| CSRF / input                  | Mutating JSON APIs require the exact configured origin and JSON content type, bounded bodies and Zod validation. Auth has an endpoint allowlist. Multipart mutations have the same origin check and reject repeated/unknown fields.                                                                                                                                                                      |
| Prices / finance              | Server derives current eligible price list, tax and delivery settings. Checkout review tokens bind the reviewed state; transaction locks recheck price/settings/eligibility. Client prices and foreign addresses cannot determine totals. Screenshots never create receipts. Bank verification requires staff permission and explicit attestation; duplicate references and self-review are constrained. |
| Payment and delivery evidence | PostgreSQL private byte storage; owner/reviewer checks on reads; no public file path. Private/no-store, PNG content type, nosniff and sandbox CSP on proof responses. Delivery proof additionally checks explicit customer sharing. Expense receipts require expense permission. Backups therefore contain private financial documents.                                                                  |
| Upload validation             | Only PNG/JPEG/WebP; 5 MiB input/output and 16 megapixel limit; actual decoder format check; single image only; re-encode PNG and sanitize filename. SVG/HTML/PDF, malformed, spoofed, repeated and oversized uploads are tested. Receipt count is bounded.                                                                                                                                               |
| SQL / database integrity      | Prisma queries and tagged parameterized raw SQL in runtime code; no runtime unsafe raw SQL call found. SQL-shaped report search is exercised as data. Constraints, immutable-history triggers, transactions, advisory/row locks and idempotency keys protect stock, receipts, costs, revisions and dispatch. Test-only fault-injection SQL is restricted to the isolated test database.                  |
| CSV                           | Same server permissions, source and filters as JSON. Shared encoder quotes cells, escapes embedded quotes and prefixes string formulas beginning with optional whitespace then `=`, `+`, `-` or `@`. Typed financial negatives remain numeric. Protected financial columns are omitted for operational admins; proof bytes, bank references and private internal delivery remarks are excluded.          |
| Logs / errors                 | API errors expose safe categories/request IDs, not raw exceptions. Environment errors report field names only. Better Auth logger emits bounded metadata. Request/browser-to-terminal logging is disabled to avoid recovery-link leakage. Expected fault-injection errors produce sanitized events. Production host/proxy/log-collector redaction and retention still require verification.              |
| Secrets / local storage       | `.env`, `.env.test`, generated clients, test output and `.local` are ignored; only `.env.example` is tracked. Inspected local environment files are mode 0600 and `.local` / test-mail directories 0700. No credential values were copied into these reports. Database archive permissions do not provide encryption.                                                                                    |
| Dependencies                  | The executed npm advisory query reported zero known vulnerabilities for the lockfile. This is a point-in-time service result, not proof that dependencies have no undiscovered vulnerabilities. No dependency or security validation was weakened.                                                                                                                                                       |

## Residual limitations

Resolved financial-integrity finding FIN-01: payment-method reports originally intersected actual payment/submission methods with checkout intent. Corrected the source query after reproducing the omission with a failing integration test, then exercised separate bank receipts/refunds and UPI totals. This was a reporting omission, not an unauthorized transfer or alteration of stored payment records. See the final audit report and execution results.

No live bank transfer, payment gateway, courier API, external email delivery, Internet exploit exercise, hosted failover/load test, physical device test or production credential test was performed. Browser mobile coverage uses Chromium emulation. Financial records lacking original lot costs remain incomplete by design; they must not be patched with fabricated prices. Historical records written under an older non-UTC database session need a provenance review before financial use; no bulk timestamp correction was attempted.

No demonstrated critical API authorization, private-file exposure, price-tampering or stock-integrity exploit remains from the executed regression coverage. That observation does not close the high-severity identity and production-access gates above.
