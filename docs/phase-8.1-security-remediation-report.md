## Privileged identity, enrollment and session enforcement

The only new application functionality is the security work expressly requested in Phase 8.1; purchasing, inventory, pricing, order, payment, dispatch and reporting features were not expanded.

- `/account/security` lets an authenticated person request their own expiring email verification link and enroll a TOTP authenticator using their current password. SMTP/file delivery uses the existing private mail infrastructure. Dummy file mail is for tests/local work only; production continues to reject file delivery. Successful email verification is audited and does not automatically create a session or grant privileges.
- TOTP setup returns a private setup key and recovery codes to that account only. The library stores encrypted factor/recovery material. `skipVerificationOnEnable` and passwordless enrollment are disabled. A correct authenticator code must confirm enrollment; a recovery code cannot substitute for the initial confirmation. The UI clears the displayed setup/codes after confirmation.
- Credential login for an enrolled account returns a bounded MFA challenge, with no usable authenticated session until factor verification. `/two-factor` supports the authenticator or a saved recovery code. Password-only, old/pre-enrollment or client-forged assurance fields never confer admin permission.
- Central `getActor` permission derivation re-reads current email/factor state and the actual stored session's assurance. ADMIN/SUPER_ADMIN receive only ordinary account permissions until all checks pass. Assurance older than twelve hours or dated in the future is rejected for privileged access. This applies in development/test as well as production; there is no MFA bypass switch for tests.
- Every session starts with null assurance, including library session rotation. Only a successful factor endpoint can stamp it. The after-hook checks current active user and confirmed factor under a per-user database lock, records the assurance/audit event, and revokes other unverified sessions. If completion fails after the library created a session, that new session is removed rather than left usable.
- Hashed TOTP replay evidence is checked for 120 seconds, covering the library's accepted time window. A pre-library check prevents a replay from clearing accumulated verification failures; a locked after-hook check additionally prevents concurrent reuse. No raw authenticator code is stored. Records are retained; no cleanup was used to erase audit/test evidence. Backup codes use the library's atomic one-time consumption; concurrent use is tested.
- Sign-in challenges expire after five minutes. Persistent library limits include per-IP throttles, bounded challenge attempts and a ten-failure/fifteen-minute account lockout. The application additionally enforces and counts account lockout for enrollment/step-up on existing password sessions, so that alternate route cannot evade the sign-in budget.
- Trusted-device requests, email OTP, public factor disable/secret redisclosure, social/username/phone login and public promotion routes are not exposed. Backup-code regeneration requires the current password plus MFA no older than fifteen minutes. Password reset revokes sessions and leaves the enrolled authenticator in place.

The production operator service still requires explicit enablement, approved operator attribution, exact existing user ID and active verified identity. It additionally checks confirmed enrollment and revokes sessions on promotion. The CLI alone uses the explicitly authorized operator DB client; ordinary web DB clients always enforce the runtime-role guard. Existing local promotion can establish a role for setup, but it cannot bypass the same privileged web gate. No real administrator was created/promoted or impersonated.

## Access, secrets and recovery controls

Runtime database connections in production check effective role flags, membership, application-object ownership and schema/database creation privileges before application queries. Privileged/owning roles fail closed. Group-role provisioning and ownership changes remain operator actions; [the SQL template](production-database-roles.sql) was not applied to a live environment. Random isolated test roles were removed after their drill; no existing business data was dropped.

Remote connections use an explicit TLS object with `rejectUnauthorized: true`; `sslmode=verify-full` is required and removed from the forwarded URL so parser options cannot override that object. A private CA can be supplied through the dedicated CA-file setting. Loopback exceptions are for genuinely private co-hosted/local PostgreSQL only. Connection-target overrides, including `host` and `options`, are rejected; test isolation also rejects them and refuses aliases to the development database. This follows the inspected node-postgres connection parser behavior, not an assumption that a URL hostname alone determines the destination.

The existing session revocation, same-origin JSON/multipart checks, upload decoding/re-encoding, role/owner proof isolation and sanitized HTTP errors remain. New audit records contain actor/entity IDs and fixed reasons, never passwords, setup keys, TOTP/recovery codes, cookies or proof bytes. Environment validation names invalid fields without printing values; production connection failures are sanitized. MFA factor encryption depends on the configured auth-secret version: backup/key escrow and tested rotation are explicit owner actions, not something to improvise by clearing factors.

There is no public emergency authentication bypass. Normal lost-device recovery needs password plus an unused saved code. Lost-all-factors intervention remains a controlled, independently verified operator incident procedure requiring revocation/removal of privileged access before replacement, fresh real verification and approved promotion. The owner must approve/rehearse that process; no real emergency account or factor reset was performed.

## Raw integrity scan investigation

The retained Phase 8 order contains an intentionally inserted 100-paise `QA unreserved line` without its matching reservation. The Phase 6 negative case uses a privileged test client to create that malformed state, then asserts dispatch is rejected. It is not a normal order-writing path or production seed.

Added a reusable guarded, read-only `npm run audit:integrity` command. It keeps all five raw invariant checks and **still exits 1 for any raw violation**, including expected fixtures. Classification separately requires prior audit/current test provenance, the actual extra unreserved line, a dummy test owner and no dispatch. New executions of the existing negative case leave private provenance files; the original Phase 8 evidence remains intact. Missing/unexpected provenance cannot silently convert a finding into a pass.

The scanner also checks the known fixture IDs against the separate loopback development database in a read-only transaction. Its actual counts and classifications are in the test-results document. No real production database was connected to certify its contents; production must never receive a test restore. Synthetic fixtures can affect synthetic aggregate reports inside the test database, which is why the report retains them as raw findings rather than claiming all test data is arithmetically clean. The isolation guard and failed-dispatch check establish their boundary from normal development/production operations.

## Migration, regression and evidence preservation

One additive migration adds the default-false factor flag, nullable session assurance, encrypted factor table and hashed replay-evidence table. It does not invent enrollment/verified identities or mark old sessions as MFA-verified. Only the isolated test database was migrated here; actual development/staging/production schema changes require the reviewed environment procedure. The repository migration count is now thirteen.

Existing staff fixtures were upgraded to request actual dummy verification links and prove actual TOTP codes before receiving privileged test access. Positive authorization tests therefore exercise the production permission gate. The independent test TOTP implementation derives RFC 6238 codes from each dummy enrollment secret. No real payment, SMTP delivery, customer/supplier/inventory update or production role change occurred.

The first full regression exposed outdated bootstrap/browser setup and UI synchronization/loading assumptions. Fixes preserve the original business assertions and backend validation. Every failed execution, actual correction, rerun and final outcome is listed in the companion test-results document. The four original Phase 8 reports, saved JSON/logs, malformed-order evidence and backup manifests/archives were retained. **Evidence-retention limitation:** early reruns reused shared screenshot/Playwright output paths and overwrote some older PNG versions and failure attachments before archival was added. Those originals were not recovered. The runner now preserves unique private before/after snapshots and fails if preservation fails; the final reporting run exercised it successfully. Phase 8.1 artifacts use a separate private directory. This correction protects future evidence and does not erase the historical gap.

## Final local evidence and decision

The stronger replay regression exposed a real failure-budget flaw: the authentication library reset accumulated failures before the after-hook rejected a replayed code. Pre-library replay rejection plus serialized counter updates corrected it; all twelve dedicated security cases then passed. This defect, the initial fixture/UI failures and their reruns are retained in the test-results document.

Final deduplicated coverage is **349 passed checks: 46 unit, 222 API, 30 desktop, 30 mobile and 21 production-build smoke checks**. The last full suite was 281/282; its one dashboard loading assertion was corrected and the entire affected reporting suite passed 40/40 with unchanged application security code. Production-mode privileged auth also passed using a real restricted test role and actual dummy factor. Build, TypeScript, lint, schema validation, thirteen-migration status and backup/restore passed. The local restore verified 56 tables and four sequences and replayed all thirteen migrations.

The raw integrity scan **remains FAIL/exit 1**: four expected negative order fixtures, zero unexpected findings, zero fixture matches in development. Other raw invariants were clean; 2,321 missing-cost test lots remain informational/incomplete. Neither fixtures nor findings were removed. The initial production smoke fetch assertion was corrected to verify the framework's streaming redirect in a browser; all 21 checks then executed successfully.

**Decision: CONDITIONAL PASS.** No known unresolved critical/high application-code defect remains in this scope after local tests. SEC-01/02/03 remain release gates insofar as they require real identities, production access and external configuration evidence. Follow the owner-action list before production approval; local results do not establish those external prerequisites. The historical screenshot-retention gap is explicitly recorded above and in test results.
