# Phase 8.1 owner actions

Phase 8.1 implements local security controls; it does not create or certify a production identity, hosting account, SMTP provider or backup service. No deployment is authorized. The four Phase 8 documents remain historical evidence. Read the [remediation report](phase-8.1-security-remediation-report.md) and [executed results](phase-8.1-test-results.md) before approving a release.

## SEC-01: real staff identities and factors

Owner / security administrator must:

1. Identify each actual ADMIN/SUPER_ADMIN independently, approve their responsibilities, and retain the approval/change reference in an access-controlled record. Email ownership is a technical check, not proof of the person's business authority. No real staff identity was verified in this exercise.
2. Have that person register their own account in the intended environment. Configure and prove actual recovery/verification SMTP delivery over TLS first. The person opens their own expiring verification link from `/account/security`; do not edit `emailVerified` manually or use a QA mailbox as a real identity.
3. Have the person enroll their own authenticator from `/account/security` using their password, save the ten recovery codes privately/offline, and enter the real six-digit TOTP code. Setup alone does not enable MFA. Keep setup keys, codes and email links out of logs, reports, screenshots, tickets and chat.
4. Use the existing controlled operator promotion process with exact user ID, operator attribution, independently verified identity and an approved reason. Production promotion now refuses unverified email or unconfirmed authenticator enrollment. The operator CLI revokes sessions; the person must sign in again and complete MFA. The console/operator identity also needs MFA and short-lived credentials. A supplied `--operator` string alone is not proof of operator identity; retain IAM/console evidence.
5. Test that password-only, expired-assurance, wrong-role, suspended and revoked sessions cannot access admin pages, financial CSV or payment review, and that correct MFA permits only the intended role's permissions. Privileged session assurance lasts at most twelve hours; after that, verify the session again. Device trust and email OTP are not enabled as substitutes.

Existing staff without these checks remain locked out of privileged functionality. No global MFA exception, test-only bypass or default administrator identity exists. Customers/dealers retain ordinary account/purchase access without mandatory staff MFA; optional enrollment uses the same real verification flow.

## Recovery and emergency access

- Password reset revokes sessions and preserves the authenticator. A mailbox/reset token alone cannot restore administrator access. Existing single-use password-token protections remain in force.
- A stored, unused recovery code is an alternative second factor **after password authentication**, not a standalone login link. Use the recovery-code option on the MFA sign-in screen. Each successful use consumes the code and records an MFA audit event. It does not disable MFA or reveal the authenticator secret.
- The authenticated backup-code regeneration endpoint requires the current password and MFA assurance no older than fifteen minutes. Reverify at `/two-factor` if necessary. Protect replacement codes exactly like the originals; there is no password-only factor rotation/disable endpoint.
- If all factors and codes are lost, keep the account locked. There is no public emergency login or self-service MFA removal. Use another independently verified administrator or the controlled operator incident process. Independently reverify the person, suspend/revoke access, preserve audit evidence and require an approved recovery/change record before any operator intervention. Any approved factor replacement must first remove privileged access, revoke sessions/challenges, audit the intervention, and require email verification, new TOTP confirmation and fresh approved promotion. Do not leave an existing privileged role usable with a cleared factor or manually stamp session assurance. This operator-only last-resort intervention is a documented approval procedure, not a new automated reset command; it was not executed on a real identity.

The owner must approve the emergency procedure, designate operators, and rehearse recovery on acceptance accounts before launch. TOTP is not phishing-resistant; HTTPS, trusted devices, secret handling and session protection remain necessary.

## SEC-02: actual production database access

- Provision separate runtime, migration/operator and backup credentials. A review template is provided in [production-database-roles.sql](production-database-roles.sql); it was not applied to a production system. It creates NOLOGIN group roles and grants, not business identities or passwords. Substitute the actual database, review ownership/default privileges and hosting-specific limitations, then provision login identities through the approved secret store. Do not copy the local bootstrap superuser or test-role credentials.
- The runtime login must not own application objects/schema/database, create schema/database/roles, bypass RLS, replicate, inherit privileged roles or belong to PostgreSQL's predefined `pg_*` capability groups. Runtime cannot use the operator-client escape hatch through a public API. The runtime adapter checks the effective role on connection and fails closed; repeat checks and restart after permission changes.
- Use the actual remote hostname and `sslmode=verify-full`. The application supplies `rejectUnauthorized: true`, forbids connection-target/TLS URL overrides, and supports an optional trusted CA bundle through `DATABASE_SSL_CA_FILE`. Verify certificate chain/hostname and rejected bad certificates against the selected production endpoint. Local tests prove option enforcement, not that an external endpoint has the correct certificate.
- Loopback PostgreSQL is allowed for a genuinely private, co-hosted server. Verify it binds only to the intended private interface and is protected from external access. The query-string `host`/`options` trick cannot convert a loopback URL into an unverified remote connection. Test tooling also refuses such target overrides.
- Restrict DB network ingress and outbound application access, confirm UTC sessions and pool budgets, and test `npm run db:health` with the **actual runtime environment**. Confirm attempted table/trigger/role creation fails. The migration/operator role is separately authorized; never grant its membership to runtime. Migrations must retain their original custom SQL constraints and triggers.
- The ordinary web environment must not contain `FIXUP_ALLOW_PRIVILEGED_OPERATIONS` or `FIXUP_PROCESS_ROLE`. Production promotion sets its operator process role internally after validating the explicit operator request. Do not persist this flag in a service environment.

Only isolated random test roles were created and removed locally. No real database login, grant, ownership, firewall or certificate was changed. Apply the thirteenth reviewed migration and regenerate/restart in approved development/staging environments before using the new security pages. Only the isolated test database was migrated during this work.

## SEC-03: production configuration, backup and monitoring

- Inject `APP_ENV=production`, the exact canonical HTTPS auth origin, a new strong auth secret, actual authorized SMTP sender/provider and runtime database credential using the hosting secret store. A production Next.js build or `NODE_ENV=production` alone is not environment approval. Build a fresh reviewed artifact with the approved target configuration; this audit’s local `.next` build used isolated test settings and must not be deployed. The local file-mail/HTTP environments remain local.
- Prove HTTPS redirects/termination, Secure/HttpOnly/SameSite cookies, trusted origin handling, CDN no-store behavior for private/auth responses and ingress client-IP sanitization. Configure `TRUSTED_IP_HEADER` only when ingress overwrites it. Verify auth/MFA throttling through that actual proxy rather than allowing a client to choose its own IP identity.
- Complete the remaining medium findings SEC-04/05: review a tested script CSP/HSTS policy and real request/body/concurrency/time limits. The existing application limits and upload re-encoding stay enabled. Exercise realistic reporting/upload volume in staging; no load/failover result was invented here.
- Establish encrypted offsite backups, separate backup credentials/key custody, restricted archive access, retention, an accountable operator and accepted RPO/RTO. Backup role needs approved data/sequence reads; it must not be the application's schema owner. The local fidelity drill uses private dummy archives, not configured production encryption, scheduling or offsite storage.
- Backups now include encrypted MFA seeds/recovery material, hashed replay evidence, authentication data and private payment/delivery/expense images. Secure the database archive and **separately** escrow the correct auth/encryption-secret version. Blindly rotating/discarding `BETTER_AUTH_SECRET` can make stored factors unreadable. Rehearse key rotation/recovery with the installed authentication library and preserve required old key material securely; no production rotation was performed.
- Restore to a fresh isolated database; verify schema, counts, hashes and critical records; recreate least-privilege grants because dumps omit roles/ACLs. Revoke restored sessions and pending recovery/MFA challenges before traffic, reconcile post-backup payments/orders/stock, and require fresh MFA. Never restore test data or the deliberate malformed fixture into production. Review the [existing restore procedure](operations.md).
- Route sanitized auth/application failures, MFA lockout rates, privileged role/session changes, provisioning failures, database pressure and backup/job failures to an accountable operator. Logs must exclude passwords, TOTP/setup/recovery codes, auth cookies, verification/reset query strings and private proof bytes. Verify proxy/provider redaction and alert delivery; no external alerts or email were sent by this work.
- Schedule and monitor the existing protected reservation-expiry command. Keep the runtime role separate from migration/operator jobs, drain batches safely and alert on backlog/failure. No public cron endpoint or scheduler was created.
- Repeat release checks on the selected Node 24 runtime/image and chosen staging ingress. This workstation's executed tests use Node 26.4.0. Record owner acceptance and rollback criteria before requesting any later deployment approval.

## Integrity fixture acceptance

The raw scanner remains strict: `npm run audit:integrity` exits 1 whenever any invariant is violated, even when the record is classified as an expected fixture. It accepts only the guarded local test environment and preserves all findings. Confirm the retained Phase 8 fixture and any freshly generated negative-test fixtures have zero matching IDs in the separate development database, remain undispatched, and have recorded test provenance. A missing provenance file or unexpected record is an investigation, not an exception to the scan. No real production database was accessed to claim it is clean.

These are explicit owner/environment actions. They are not silently marked complete by local tests, and this document authorizes no deployment or real-data changes.
